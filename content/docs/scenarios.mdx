## S1. 결제 SDK 어떻게 정하지?

### 상황

신용금융회사 모바일 앱 신규 팀. A는 Claude Code 사용자, B는 Codex CLI 사용자다. A가 결제 기능을 담당하게 되고 토스페이먼츠 SDK를 채택하기로 결정했다. 그 다음날 B가 결제 모듈에 손을 댄다.

### oma 없이

> A: 토스페이먼츠로 결제 만들었어. 결제 요청 흐름이 이렇게...
>
> B: (다음날) 어? 이거 왜 토스페이먼츠여? 우리는 이니시스 쓸 줄 알았는데.
>
> A: 아, 내가 정하고 코드만 짰어. 옛날 프로젝트는 이니시스를 써서...
>
> B: Slack에 얘기 안 해줬어? 지금 이니시스 기반으로 절반을 이미 만들어 버렸어.
>
> (결과: 30분 Slack 핑퐁 → 코드 롤백 → 누가 결정할 건지 불명 → 경영진 확인 → A가 다시 코드)

### oma 있을 때

> A: 토스페이먼츠 가자. ADR로 남기고 시작한다.

```bash
/oma:adr new "결제 SDK 선택"
```

결과:

```
adr/0007-결제-sdk-선택.md 생성됨
```

ADR 내용(일부):

```markdown
# 0007. 결제 SDK 선택

## 결정
토스페이먼츠로 통일한다.

## 근거
- 신용금융사 본인인증 SDK 최신 버전 지원
- 국내 개발 진흥원 등록 완료 (감리 필요서류)
- 팀원 경험도: 높음(이전 3개 프로젝트)
```

> B: (다음날 세션 시작)

Codex CLI 세션 시작 시 hook이 자동 실행되고:

```
✓ Project config found: .oma/config.yaml
✓ ADR-0007 감지: 결제 SDK 선택 → 토스페이먼츠 채택됨
```

화면에 ADR 요약이 뜨고, B는 결정을 5초 만에 확인할 수 있다.

> B: 아, ADR-0007 있네. 토스페이먼츠로 가는 거구나. 나는 이니시스 부분 롤백할게.

### 뭐가 달라졌나

- **자동 공유**: 비가역 결정이 Slack이 아니라 `adr/`에 산다. 새 세션이 시작되면 hook이 자동으로 ADR을 표면화한다.
- **근거 남음**: 왜 토스페이먼츠인지를 나중에 읽을 수 있다. 6개월 뒤 새 팀원도 같은 이유를 본다.
- **충돌 방지**: 결정을 먼저 기록하고 코드를 짜서, 중복 작업을 처음부터 방지한다.

## S2. AI가 만든 결제 모듈, 진짜 우리 코드가 맞나?

### 상황

C는 Claude Code를 쓰는 Android 솔로 개발자다. 팀 profile에는 DI를 Hilt로 통일했고(ADR-0004), 결제 SDK는 data layer에서만 캡슐화하기로 했다(ADR-0005). C가 "결제 confirm 화면 만들어줘"라고 AI에게 요청했고, AI가 ViewModel + DI 모듈을 빠르게 뽑아냈다. 컴파일은 일단 된다.

### oma 없이

```kotlin
// AI가 생성한 PaymentViewModel.kt
@HiltViewModel
class PaymentViewModel(
    private val tossClient: TossClient = get()  // Koin의 get()
) : ViewModel() {
    fun confirm(order: Order) {
        val result = TossPayments.confirmPayment(  // v4.2에 없는 메서드
            order = order, authToken = token
        )
    }
}
```

C가 빌드를 돌린다. `confirmPayment` 미존재 컴파일 에러. 공식 문서를 보고 `requestPayment`로 바꾼다. 빌드 성공, 화면 동작 OK. 머지.

> C: (2주 뒤, 같은 모듈에 카드 등록 기능 추가 중) 어? 다른 ViewModel은 Repository를 거치는데 PaymentViewModel만 SDK를 직접 부르네. Koin import도 여기만 남아있고…
>
> (ADR-0005 다시 읽음) "결제 SDK는 data layer에서 캡슐화한다."
>
> C: 내가 쓴 ADR을 내가 어겼다. 그것도 2주 동안 모르고.
>
> (결과: AI가 만든 1시간 분량 코드 → 2주 뒤 발견 → 모듈 재배치 + DI 리팩토링 반나절)

컴파일러는 SDK 환각만 잡는다. 프레임워크 불일치와 ADR 위반은 침묵한다.

### oma 있을 때

C는 AI 코드를 받은 직후, 머지 전에 verify를 돌린다:

```bash
oma verify --path ./feature/payment --json
```

결과:

```json
{

  "scan_type": "verify",
  "scope": "./feature/payment",
  "results": [
    {
      "policy_id": "profile-consistency",

        "feature/payment/di/PaymentModule.kt:7",

      ],
      "note": "Profile은 Hilt 선언. 그러나 org.koin.core.* import 발견. DI 프레임워크 불일치."
```

> C: 한 번 돌렸는데 세 군데가 떴다. DI 프레임워크가 섞였고, ADR-0005를 위반했고, 그 줄에 환각 메서드까지 있다.

C는 AI에게 정리해서 다시 요청한다: "Hilt만 써. SDK 호출은 PaymentRepository로 옮겨. v4.2의 requestPayment 써." AI가 재생성 → verify 재실행 → 5/5 pass. 머지.

### 뭐가 달라졌나

- **한 번에 다섯 정책을 본다**: profile, ADR, SDK 환각, 성능, 요건 커버리지가 같은 형식으로 보고된다. 컴파일러가 잡지 못하는 구조적 위반이 컴파일 에러와 나란히 드러난다.
- **팀 결정을 코드가 기억한다**: AI는 이 팀이 Hilt를 쓰는지, ADR-0005가 뭐라 했는지 모른다. verify는 안다.
- **솔로일수록 더 산다**: 리뷰어가 없는 환경에서 2주 뒤에야 발견되던 것을, 코드 받자마자 잡는다.

## S3. 3개월 뒤 새 멤버가 들어왔다

### 상황

팀에 처음으로 들어온 신입 개발자 D가 있다. 기존 팀원 A, B는 휴가 중이다. D가 결제 모듈의 코드를 보고 있는데 구조가 낯설다. "왜 이렇게 만들었지? 왜 토스페이먼츠는 별도 모듈로 떨어져 있지?"

### oma 없이

D가 Slack 히스토리, 옛날 PR, 파일 blame을 뒤진다:

> (D가 git log 확인 중) A: payment/toss.swift 생성 - 토스페이먼츠 SDK 로직
>
> (D가 그 PR 메시지 확인) → "SDK 로직 분리" (너무 짧은 메시지)
>
> D: (A, B와 연락 안 됨) 일단 내 감으로 구조를 이해하고 코드를 짠다.
>
> (결과: 처음부터 구조를 모르고 짠 코드 → 나중에 A가 리뷰하면 "이건 우리 구조 아니야" → 다시 작성)

### oma 있을 때

D가 `adr/` 디렉토리를 열어본다:

```
adr/
├── 0001-모듈-구조-선택.md
├── 0002-인증-플로우.md
├── 0003-결제-sdk-선택.md
├── 0005-SDK별-모듈-분리.md
├── 0006-Feature-기반-모듈-구조.md
├── ...
```

D가 ADR-0006을 본다:

```markdown
# 0006. Feature 기반 모듈 구조 채택

## 결정
Feature 단위로 모듈을 분리한다.
- payment/ (결제 도메인)
  - payment/core (통합 계약)
  - payment/toss/ (토스페이먼츠 구현)
  - payment/pg/ (향후 다른 PG 추가 가능)

## 근거
- SDK별로 구현이 다르므로 나중에 PG 추가 시 payment/toss와 
  결합도를 낮출 수 있다
- 국내 앱은 보통 다중 PG를 지원해야 한다 (감리 요구)

## ADR-0003의 토스페이먼츠 선택과 함께,
이 구조로 향후 NHN KCP나 NICEPAY 추가 시
payment/toss와 payment/nicepay를 독립적으로 개발할 수 있다.
```

> D: 아, 처음부터 다중 PG 대비를 했구나. 그래서 payment/ 아래에 toss/, pg/ 같은 폴더가 있는 거네.

D는 구조의 '왜'를 이해한 후 코드를 추가한다. 리뷰는 5분이다.

> A: (휴가에서 돌아와) D의 코드를 보니 ADR-0006을 완벽히 따르고 있네. 좋아.

### 뭐가 달라졌나

- **결정 생존**: 팀원이 바뀌어도 비가역 결정은 `adr/` 디렉토리에 산다. 도구도, 사람도 바뀌어도 문서는 남는다.
- **onboarding 시간 절약**: 새 멤버가 처음 30분을 신경 써서 읽으면, 다음 3개월 개발이 구조 오류로 낭비되지 않는다.
- **미래 기능 추가**: ADR-0006이 "향후 다른 PG 추가 시"라고 명시했으므로, 나중에 NICEPAY를 추가할 때 이 구조를 따른다.

## S4. "AI야 그냥 바꿔" — 바이브코딩이 아키텍처를 부술 때

### 상황

E는 결제 모듈을 담당하고 있다. 토스페이먼츠로 결정된 상태(ADR-0007)이고, 다중 PG를 대비한 모듈 구조도 잡혀 있다(ADR-0006). 어느 날 기획에서 "이니시스도 지원해야 한다"는 요구가 들어왔다. E는 Claude Code에 이렇게 말한다:

> E: 결제를 이니시스로 바꿔. 토스페이먼츠 코드 걷어내고 이니시스 SDK로 교체해.

### oma 없이

AI가 즉시 실행한다:

```kotlin
// 토스페이먼츠 코드 삭제
// 이니시스 SDK import
val result = InicisPayment.requestPay(
    merchantId = "...",
    amount = order.total,
    productName = order.name
)
```

> E: 돌아간다. 머지하자.
>
> (다음날) F: 어? 토스페이먼츠 코드가 다 없어졌는데? ADR-0006에서 다중 PG 구조 잡아놨잖아. 왜 교체야? 추가여야 하는 거 아니야?
>
> E: 기획에서 바꾸래서...
>
> F: 바꾸라는 거랑 추가하라는 거랑 다르잖아. 기존 토스 결제 유저는?
>
> (결과: 롤백 → 기획 재확인 → "추가"였음 → E가 처음부터 다시 작업)

### oma 있을 때

E가 "결제를 이니시스로 바꿔"라고 입력한다.

AI가 `AGENTS.md`의 ADR-first 규칙을 따라 `adr/`을 먼저 확인한다. 기존 결정과 충돌을 발견하고 멈춘다:

```
⚠ 비가역 결정 충돌 감지

현재 요청이 기존 ADR과 충돌합니다:
  • ADR-0007: 결제 SDK → 토스페이먼츠 채택
  • ADR-0006: Feature 기반 모듈 구조 → 다중 PG 대비 설계

"교체"는 두 ADR을 동시에 뒤집습니다. 확인이 필요합니다:

1. 토스페이먼츠를 완전히 제거하고 이니시스로 교체?
   → 새 ADR 필요 (ADR-0007 supersede)
2. 이니시스를 추가 PG로 병행 지원?
   → ADR-0006 구조를 따라 payment/inicis/ 추가
3. 기획에 다시 확인?
```

> E: 아... 기획한테 다시 물어볼게.
>
> (기획 확인 → "추가"였음)
>
> E: 이니시스를 추가 PG로 넣어줘.

AI가 ADR-0006의 다중 PG 구조를 따라 `payment/inicis/`를 생성한다. 기존 `payment/toss/`는 그대로.

### 뭐가 달라졌나

- **비가역 변경 전에 멈춘다**: `AGENTS.md`가 AI에게 ADR-first 규칙을 심는다. "그냥 바꿔"가 곧바로 실행되지 않고, 기존 결정과 충돌하면 먼저 물어본다.
- **교체 vs 추가를 구분한다**: 기획 의도를 개발자가 한 번 더 확인하게 된다. 30분 롤백 대신 30초 확인.
- **기존 아키텍처를 보호한다**: ADR-0006의 다중 PG 구조가 바이브코딩 한 번에 날아가지 않는다.
