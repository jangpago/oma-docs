## 문제

AI가 개발에 들어오면서 전에 없던 문제 세 가지가 생겼다.

1. **AI는 팀의 결정을 모른다.** Hilt로 통일했는데 AI가 Koin으로 짠다. ADR-0005에서 SDK를 data layer에 캡슐화하기로 했는데 AI가 ViewModel에서 직접 부른다. 세션이 바뀌면 맥락이 날아간다.

2. **AI는 "동작하는 코드"와 "우리 코드"의 차이를 모른다.** 빌드 통과해도 모듈 구조가 어긋나 있고, ADR이 금지한 패턴이 살아 있고, profile에 선언한 프레임워크 대신 다른 게 섞여 있다. 컴파일러는 이걸 검사하지 않는다. 동작하니까 머지하는데, 2주 뒤에 구조가 꼬인다.

3. **팀원마다 다른 AI를 쓴다.** 한 명은 Claude Code, 한 명은 Codex, 한 명은 Cursor. 도구는 셋이어도 비가역 결정과 검증 기준은 하나여야 한다.

oma는 이 셋을 잡는 얇은 하네스다. ADR로 결정을 기록하고, `verify`로 AI가 만든 코드가 그 결정과 맞는지 검사하고, `AGENTS.md`로 어느 도구든 같은 규칙을 읽게 한다.

## 비교: oma 없을 때 vs 있을 때

| 문제 | oma 없을 때 | oma 있을 때 |
|---|---|---|
| **AI가 결정을 모른다** | Hilt인데 Koin으로 짠다. 세션 바뀌면 맥락 소실 | ADR + hook이 세션마다 결정을 주입. AI가 팀 규칙을 읽고 시작 |
| **컴파일러는 구조 위반을 모른다** | 사람이 일일이 봐야 하고, 누락된 위반은 2주 뒤 발견 | `verify`가 profile 일치, ADR 준수, 모듈 구조를 한 번에 검사. merge 전에 잡음 |
| **도구가 다르다** | Claude Code 쓰는 사람과 Codex 쓰는 사람의 기준이 다름 | `AGENTS.md`가 도구 독립 정본. 어떤 AI든 같은 규칙 |

## oma가 하는 일

1. **프로젝트 컨텍스트를 구조화한다** — `AGENTS.md`, `project_profile.yaml`, 정책을 같은 형식으로 정의해서 다음 사람과 다음 세션이 이어받을 수 있게 한다.

2. **생성 결과를 정책으로 검증한다** — SDK 메서드 존재 여부, 권한 체크, 보안 제약을 자동으로 검사해서 AI 환각을 merge 전에 포착한다.

3. **비가역 결정을 ADR로 기록한다** — 기술 선택, 모듈 구조, SDK 통합, 보안 정책 같은 한 번 정하면 돌리기 어려운 결정을 `adr/` 폴더에 남겨서 나중에 "왜 이렇게 했지?"를 1분 안에 이해한다.

4. **검증 증거로 사람이 승인할 근거를 남긴다** — 정책을 통과했는지 JSON으로 기계가 읽을 수 있게 남겨서 "감으로 승인"하지 않고 증거를 보고 승인한다.

## oma가 아닌 것

- 앱 기능 코드베이스를 만들어주는 도구가 아니다.
- 린트나 CI를 대체하는 도구가 아니다.
- 특정 AI 도구(Claude Code, Codex, Cursor)에만 묶인 플러그인이 아니다.

oma는 어떤 도구든 같은 규칙을 적용하려고 도구 독립적으로 만들었다. 따라서 정본은 `AGENTS.md` 파일이고, Claude Code는 그 정본을 어댑터로 연결하는 방식이다.
