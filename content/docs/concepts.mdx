oma는 큰 한 덩어리가 아니다. 4개의 작은 장치가 각각 다른 실패를 막는다.

## 4개 장치

| 장치 | 막는 실패 |
| --- | --- |
| ADR-first | "왜 이렇게 짰지?"가 안 남는 문제 |
| 정책 카탈로그 | AI 환각이 production까지 새는 문제 |
| Overlay | 도메인/환경 제약이 뒤늦게 붙는 문제 |
| Anti-slop 게이트 | 쓸모없는 자동화가 쌓이는 문제 |

## ADR-first — "왜 이렇게 짰지?"가 안 남는 문제

3개월 뒤 자기가 짠 코드도 왜 이렇게 했는지 모른다. 팀이 늘어나면 A가 정한 결정을 B가 모르고 롤백한다. 초기에 굳힌 선택 하나가 이후 6개월 비용을 결정하는데, 그 결정의 근거가 Slack 메시지 어딘가에 파묻혀 있다.

코드보다 ADR(Architecture Decision Record)이 먼저다.

이런 결정이 보이면 코드 작성 전에 멈춘다.

- 기술 스택 선택
- 모듈 경계와 의존성 방향
- 핵심 SDK 채택 또는 교체
- 환경 분리 방식
- 인증, 결제, 보안, 권한 플로우
- CI/CD나 배포 흐름

**규칙**: 코드 먼저 쓰고 ADR 나중에 작성하는 흐름은 금지다.

**링크**:
- 실제 시나리오: [시나리오 S1 — 결제 SDK 어떻게 정하지?](/docs/scenarios#s1-결제-sdk-어떻게-정하지)
- 또 다른 시나리오: [시나리오 S3 — 3개월 뒤 새 멤버가 들어왔다](/docs/scenarios#s3-3개월-뒤-새-멤버가-들어왔다)
- 실제 ADR 사례: [ADR 사례](/docs/adr-examples)

## 정책 카탈로그 — AI 환각이 production까지 새는 문제

AI가 존재하지 않는 SDK 메서드를 만들어낸다. 코드 리뷰어가 매번 같은 지적을 한다면 — "SDK 메서드 진짜 있는 거 맞아?", "권한은 매니페스트에 선언했어?", "성능 이슈 없을까?" — 그 지적 목록을 정책(Policy)으로 만든다.

정책은 `/verify` 단계에서 AI가 읽고 따르는 검증 지침이다. 존재하지 않는 코드, 충돌하는 제약, 건너뛴 기능을 배포 전에 잡는다.

Base 정책:

- **profile-consistency**: Profile 선언과 코드의 일치
- **adr-compliance**: 승인된 ADR이 코드에 반영됨
- **sdk-hallucination**: 존재하지 않는 SDK 메서드/클래스
- **performance-impact**: 메인 스레드 네트워크 호출, 비효율적 루프
- **requirement-coverage**: 모든 기능 요건이 사용자 접점에 연결됨

**링크**:
- 실제 시나리오: [시나리오 S2 — AI가 만든 결제 모듈, 진짜 우리 코드가 맞나?](/docs/scenarios#s2-ai가-만든-결제-모듈-진짜-우리-코드가-맞나)
- 정책 상세: [정책 카탈로그](/docs/policies)

## Overlay — 도메인/환경 제약이 뒤늦게 붙는 문제

금융 앱이면 본인인증 SDK가 필수다. 한국 SI 프로젝트면 감리 증적이 필요하다. Messenger 앱이면 E2E 암호화를 고려해야 한다. 이건 프로젝트마다 다르고, 초기에 정해야 한다.

정책과 검증은 4단계로 쌓인다.

```text
base (공통) → industry (산업군) → environment (운영 환경) → project (개별 프로젝트)
```

더 구체적인 단계가 앞 단계를 덮어쓴다. 충돌하면 ADR에 우선순위와 이유를 남긴다.

**예시**: mobile industry overlay가 선택되면 권한 일관성(permission-consistency), API 레벨 호환성(api-level-compat) 검증이 추가된다.

**링크**: [정책 카탈로그](/docs/policies)

## Anti-slop 게이트 — 쓸모없는 자동화가 쌓이는 문제

새 자동화/명령/훅/스크립트를 추가하기 전, 아래 3문항을 먼저 통과해야 한다.

1. 이번 주에 3회 이상 반복되는가?
2. README 한 줄 또는 단일 셸 명령으로 대체 불가능한가?
3. 실패해도 수동 복구가 쉬운가?

세 문항 모두 YES일 때만 구현을 검토한다. 하나라도 NO면 만들지 않는다.

이 문서의 모든 명령도 이 게이트를 통과해서 존재한다.

## 어디에 무엇을 적나 — 결정 기록 위계

oma가 강제하는 건 모든 문서 양식이 아니다. 무엇을 어디에 남길지의 경계다.

| 단위 | 무엇 | 기록 위치 |
| --- | --- | --- |
| 요구사항 | 무엇이 필요한가 | 외부 도구, `requirements.md`, `project_profile.yaml` |
| 작업 계획 | 어떻게 만들 것인가 | Issue, PR, `WORKPLAN.md`, 프로젝트 자율 문서 |
| 비가역 결정 | 왜 이렇게 정했는가 | `adr/` |
| 검증 증거 | 실제로 충족됐는가 | Evidence Bundle |

핵심은 범위가 아니라 **되돌리기 어려움**이다. 작은 모듈 안의 결정이라도 다른 모듈 계약, 보안, 테스트, 운영에 오래 영향을 주면 ADR이다. 요구사항과 작업 계획 양식은 oma가 강제하지 않는다(각 프로젝트가 정한다).

## 부록: 아키텍처 5층 (참고)

여기까지 읽었으면 oma 내부가 어떻게 나뉘는지 볼 수 있다. 아래는 참고용 자료다. 실행 순서나 workflow를 나타내는 게 아니라, 아키텍처 구분일 뿐이다.

| 층 | 책임 |
| --- | --- |
| Core Harness | 정본, 결정(ADR), 정책, 증적(Evidence) |
| Observation | 코드, 문서, 빌드, 테스트, 런타임 관측 |
| Control Plane | 리뷰, 자율 단계, 동시작업, 엔트로피 수거, 팀 학습 침전 |
| Tool Adapter | Claude Code, Codex CLI, 도구 독립 CLI(`bin/oma`) |
| Overlay | 산업군, 환경, 고객사, 앱 제약 |
