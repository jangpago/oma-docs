## 한 줄 요약

AI가 만든 코드에 존재하지 않는 SDK 메서드가 섞여 있다. 시뮬레이터를 돌려야 알 수 있을까? oma는 그 전에 잡는다.

## check와 verify, 뭐가 다른가

두 명령 모두 코드 자체를 고치지 않는다. 다만 속도와 깊이가 다르다.

| | check | verify |
|---|---|---|
| **목적** | 빠른 건강도 스캔 | 정책 기반 심층 검증 |
| **실행 시간** | 빠름 (읽기만) | 느림 (정책 분석) |
| **실행 위치** | 언제든 | 검증 단계, 세션 종료 시 |
| **출력 형식** | 텍스트 경고 | evidence JSON (CI/감사용) |

보통은 `check` 먼저 돌려 기본 선별을 하고, 그다음 `verify`로 깊게 본다. 대체 관계가 아니라 순차 관계다.

```bash
/oma:check          # 빠른 스캔
/oma:verify         # 심층 검증
/oma:verify --json  # CI/감사 연결용
```

## "아무것도 안 걸리는 게 더 무섭다"

verify 결과가 전부 pass인데 정말 안심해도 될까?

oma는 **Coverage > Pass** 원칙을 따른다. "아무것도 안 걸렸다"는 안전이 아니라 검증 범위가 좁다는 신호일 수 있다.

**구체 예시:**

프로젝트에 8개 정책이 정의되어 있는데, verify를 돌렸더니 `sdk-hallucination` 정책만 트리거되고 나머지 7개는 "해당 없음"이라고 나온다면?

- ❌ 해석: "코드가 깨끗하다"
- ✅ 해석: "다른 7개 정책의 검사 범위에 현재 코드가 들어가지 않은 것이다"

예를 들어 `performance-impact` 정책(메인 스레드 네트워크 호출 검출)이 "해당 없음"이면, 해당 코드에 네트워크 호출이 없거나, 자동 검사 범위 밖일 수 있다. 이럴 땐 수동으로 한 번 살펴봐야 한다.

## 검증이 보는 11가지 질문

이 질문들은 팀에서 반복적으로 관찰된 실제 실패 패턴에서 나왔다. 각 정책이 이 질문 중 몇 개를 자동으로 검사하는지는 정책 카탈로그에서 본다.

| # | 질문 |
|---|---|
| Q1 | 이 변경은 프로젝트 리스크를 만들거나 키우는가? |
| Q2 | 플랫폼/모듈/SDK/환경에 미치는 영향이 명확한가? |
| Q3 | 시뮬레이터와 실제 디바이스에서 검증되었는가? |
| Q4 | 성능/권한/보안/a11y/배포 안정성에 문제가 없는가? |
| Q5 | 사람이 승인할 수 있는 근거(evidence)가 충분한가? |
| Q6 | 결과가 사용자 의도와 정확히 일치하는가? |
| Q7 | 사용한 API/SDK/메서드가 실제로 존재하는가(환각 없음)? |
| Q8 | 기존 UX/데이터 플로우와 일관적인가? |
| Q9 | 이 아키텍처 결정이 6개월 뒤에도 유지 가능한가? |
| Q10 | 선택한 기술 스택/SDK는 이후 마이그레이션이 가능한가? |
| Q11 | 신규 개발자가 1주 안에 구조를 이해할 수 있는가? |

## evidence JSON 한 번 보기

`/oma:verify --json` 실행 결과는 machine-readable JSON이다. 이 JSON을 CI에 연결하거나 감사 기록으로 남긴다.

```json
{
  "scan_id": "verify-2026-05-12T14:23:01Z",
  "scan_type": "verify",
  "scope": "./src/payment/",
  "results": [
    {
      "policy_id": "sdk-hallucination",
      "pass": false,
      "evidence_paths": ["src/payment/CompletionScreen.swift:18"],
      "note": "존재하지 않는 SDK 메서드: TossPayments.confirmPayment"
    }
  ],
  "summary": { "total": 8, "passed": 7, "failed": 1 }
}
```

감을 믿고 승인하는 게 아니라 이 JSON을 보고 근거 있게 승인한다. 파일 경로(evidence_paths), 정책 ID, 상세 메모가 모두 들어가 있어서 누가 나중에 봐도 "왜 이 정책이 걸렸는가"를 알 수 있다.

## 자동 점검 — strict 모드

코드를 쓰면서 매 순간마다 점검받고 싶으면 `/oma:strict on`을 켠다. 자세한 동작과 세부 옵션은 [훅 페이지](/docs/hooks)에서 본다.
