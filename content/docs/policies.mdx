코드 리뷰어가 매번 같은 지적을 한다고 치자. "SDK 메서드 진짜 있는 거 맞아?", "권한은 매니페스트에 선언했어?", "성능은 괜찮을까?". 그 지적 목록을 글로 적은 게 정책이다. `/verify`가 그 정책을 읽고 AI 생성 코드를 점검한다.

## 정책 하나가 동작하는 예시 — sdk-hallucination

AI가 결제 화면에 이 코드를 생성했다:

```swift
// AI가 생성한 코드
let result = TossPayments.confirmPayment(
    amount: Int(totalPrice),
    productId: orderId
)
```

### verify가 하는 일

1. **심볼 테이블 스캔**: LSP(Language Server Protocol)에서 `TossPayments.confirmPayment` 메서드가 존재하는가?
2. **공식 문서 cross-check**: TossPayments SDK v5.2 문서에 이 메서드가 실제로 있는가?
3. **판정**: 둘 다 없다. → `fail`

### 검증 결과

```json
{
  "policy_id": "sdk-hallucination",
  "pass": false,
  "evidence_paths": ["app/payment/CheckoutScreen.swift:18"],
  "note": "TossPayments.confirmPayment는 v5.2에 없다. 존재하지 않는 메서드"
}
```

### 사람이 받는 메시지

> 18번 줄: `TossPayments.confirmPayment`는 실제 SDK에 없습니다. SDK 문서를 확인하거나 `requestPayment()` 등 실제 메서드를 사용하세요.

## Base 정책 — 모든 프로젝트

| 정책 | 막는 것 | 언제 트립되나 |
|---|---|---|
| `profile-consistency` | 선언과 코드 불일치 | Profile에 "Hilt 사용"이라 했는데 Koin을 import할 때 |
| `adr-compliance` | ADR 미반영 | ADR에서 정한 구조를 코드가 무시할 때 |
| `sdk-hallucination` | AI 환각 | 존재하지 않는 SDK 메서드/클래스 호출 |
| `performance-impact` | 성능 위반 | 메인 스레드에서 네트워크/DB 호출, 비효율적 루프 |
| `requirement-coverage` | 요건 누락 | 요건은 있는데 사용자 접점이 없을 때 |

## 정책 로딩 순서

더 구체적인 단계가 앞 단계를 덮어쓴다.

```
base → industry → environment → project
```

- **base**: `plugin/policies/base/*.md` — 모든 프로젝트
- **industry**: `plugin/policies/{industry}/*.md` — 선택한 산업군 (예: mobile)
- **environment**: `plugin/policies/environment/{env}/*.md` — 운영 환경 (예: korean-si)
- **project**: `policies/*.md` 또는 `.oma/policies/*.md` — 프로젝트 커스텀

## Overlay 예시 — mobile

mobile 산업군이 선택된 프로젝트에서만 붙는 정책:

- **`permission-consistency`**: 매니페스트 선언 권한과 코드 실제 사용 권한 불일치 검출
- **`api-level-compat`**: minSdk보다 높은 API 사용 시 분기 처리 확인
- **`background-restrictions`**: 백그라운드 실행 제한, Foreground Service 타입 적합성
- **`store-policy`**: Play Store / App Store 심사 가이드라인 위반 사전 점검

## Environment — korean-si

- **`audit-evidence`**: 결정→코드→검증→배포 증적 체인 연결성 점검
- **`phase-gate`**: 단계별 게이트 통과 요건 누락 점검

## 직접 정책 쓰기

1. **목적**: 무엇을 막는지 1-2문장
2. **검증 범위**: 어떤 파일/영역을 볼지
3. **검증 방법**: 분석 절차를 단계로
4. **판정 기준**: pass/fail 조건
5. **보고 형식**: evidence에 포함할 것 (경로, 스니펫, 이유)
