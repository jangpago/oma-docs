oma는 두 자동 점검 모드를 제공한다. 기본 모드는 항상 동작하고, 엄격 모드는 필요할 때만 켠다.

## 누가 strict를 켜는가

다음 경우라면 `/oma:strict on`으로 켜는 게 낫다.

- **다인 협업에서 AI 환각이 자주 나타날 때** — SDK 메서드 오류, 잘못된 권한 사용 같은 것들이 계속 리뷰 단계에서 잡힐 때라면 사전에 차단하는 게 낫다.
- **감리/리뷰 경로가 무거울 때** — 검증 프로세스가 복잡하거나 비용이 높다면 코드 작성 시점에 자동 검증으로 피드백 루프를 줄일 수 있다.
- **높은 기준을 유지해야 할 때** — 금융/보안 같은 도메인에서 프로파일 준수가 중요하다면 엄격 모드로 편차를 줄일 수 있다.

**혼자 빠르게 prototyping 중이라면** 기본 모드를 유지하는 게 낫다. 불필요한 느림을 피하고, 나중에 `/oma:verify`로 일괄 점검하면 충분하다.

## 기본 모드 — 항상 동작

`.oma/config.yaml`이 있으면 다음 시점에 자동으로 실행된다.

| 시점 | 점검 내용 | AI 호출 |
|---|---|---|
| 코드 작성 전 | 위험 명령, 범위 밖 경로, 정책 위반 패턴 | 없음 |
| 세션 종료 | `/oma:verify` 실행 권고 | 없음 |
| 세션 시작 | 상태 파일 생성 | 없음 |

## 엄격 모드 — strict on 후 추가

| 점검 | 역할 |
|---|---|
| SDK 환각 차단 | 존재하지 않는 메서드/클래스 사전 검출 |
| 기준 이탈 확인 | 코드가 프로파일과 규칙에 맞는지 검증 |
| 권한·민감 기능 | 선언되지 않은 권한 사용 차단 |
| Overlay 정책 | 선택한 산업군/플랫폼 정책 호환성 |
| 성능 위반 | 메인 스레드 네트워크/DB 같은 기본 성능 문제 |

## 토글하기

```bash
/oma:strict on       # 엄격 모드 활성화
/oma:strict off      # 기본 모드로 복귀
/oma:strict status   # 현재 모드 확인
```

토글 후 Claude Code를 재시작해야 적용된다.

## 트레이드오프

| 모드 | AI 호출 | 비용 | 결과 안정성 |
|---|---|---|---|
| 기본 | 없음 | 낮음 | 안정적 |
| 엄격 | 있음 | API 사용량 증가 | 가능성 있음 |

## 활성화 조건

두 모드 모두 프로젝트 루트에 `.oma/config.yaml`이 있어야 동작한다. 이 파일이 없으면 어떤 자동 점검도 실행되지 않는다.
